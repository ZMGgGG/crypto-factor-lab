# Crypto Factor Lab

Crypto Factor Lab 是一个可扩展的因子挖掘与策略研究系统，长期可覆盖单资产时间序列因子、横截面多因子、市场状态因子以及其他量化策略。当前迭代使用 Binance USD-M `BTCUSDT` 1 小时数据，先把因子表达式生成、样本外评价、成本审计、去重和候选管理做成完整闭环；BTC 是当前需求和第一套验收数据，不是项目的永久边界。

当前系统可以做真实历史因子研究和后台实验，不执行真实订单，也不连接交易账户。本项目仅用于研究与工程演示，不构成投资建议。

## 核心能力

- 可复现的 Binance USD-M K 线与资金费率下载、校验和数据清单；
- 安全、可序列化的因子表达式 DSL，以及确定性候选生成；
- 训练、验证、最终留出和 purge 隔离；
- Rank IC、滚动稳定性、HAC、FDR 和相关性去重；
- 手续费、价差、滑点和资金费率成本审计；
- Qwen 结构化候选提议与本地 AST 二次校验；
- SQLite 候选目录、观察跟踪、后台任务和研究控制台；
- 单资产主流程，以及后续多资产和横截面研究所需的通用接口。

## 当前状态

已实现：

- Binance USD-M `BTCUSDT` 2021 年至最新已发布归档的 1 小时历史数据；

- 资金费率历史下载与结算时间对齐；
- 注册式手工因子基线：动量、反转、实现波动率、相对成交量、趋势效率、资金费率 z-score，用于验证生成器和评价器的回归结果；
- 未来收益标签和 4 小时 purge；
- 一年训练、三个月测试的 walk-forward；
- 手续费、半价差、滑点和资金费率成本模型；
- 同源 Python API；
- 后台实验任务和状态轮询；
- 前端真实数据集、因子列表、图表和实验提交；
- 独立观察快照、候选冻结和手动收益更新；

## 目标研究流程

```text
Binance 历史归档
        ↓
SHA-256 校验与 OHLCV 数据契约
        ↓
候选因子表达式生成
        ↓
未来收益标签
        ↓
purged walk-forward
        ↓
IC / Rank IC / ICIR / 分位收益
        ↓
手续费、价差、滑点、资金费率
        ↓
样本外筛选、因子去重和候选目录
        ↓
CSV / JSON 报告
        ↓
API 读取与前端展示
```

当前已经跑通手工基线、候选生成、时间分区筛选、验证期去重、滚动稳定性/HAC、最终留出确认、正式因子入库和前端任务。自动挖掘阶段只使用训练和验证区间，并默认要求通过 `q=0.05` 的 FDR；该数值是预注册初值，仍需用后续实验校准。风险和条件因子等待各自专用评价协议。

当前研究协议已调整：默认 200 个候选按窗口、二元表达式和深度 3 组合均衡抽样；无显式门槛时只标记为 `eligible`；自动挖掘不计算最终留出指标。因子角色和信号语义在最终确认前冻结，方向因子只在最终留出段执行成本回测。

当前新挖掘运行标记为研究协议 `2.3`：候选按验证期绝对 Rank IC 排序，统一执行 FDR 并要求通过；方向策略使用训练和验证数据拟合默认 80%/20% 入场分位阈值，再按预测周期非重叠调仓。留出揭示会写入目录账本，同一数据集和时间段不能重复作为最终留出；当前 2025 留出段已被 `2.2` 验收使用，必须增加新的未见数据后才能运行下一次最终确认。

API 会为每次运行返回 `final_confirmation_available` 和不可用原因。当前数据不足时，前端候选操作显示“等待新数据”，服务端也会在创建任务前拒绝最终确认请求，不能通过直接调用 API 绕过。

这次路线调整不需要大幅重写。现有数据、标签、评价、walk-forward、成本、报告、任务持久化和前端服务继续复用，主要新增以下模块：

| 模块 | 处理方式 |
|---|---|
| 数据契约和 BTC 数据 | 保留 |
| 标签、IC、Rank IC、walk-forward | 保留 |
| 成本模型和组合诊断 | 保留，后续补语义方向 |
| API、SQLite 任务和前端框架 | 保留，增加挖掘任务与候选页面 |
| `FactorRegistry` | 保留，职责调整为保存手工基线和最终确认通过的候选 |
| 表达式 DSL、候选生成、筛选和去重 | 已完成基础版，后续补统计和成本约束 |

因此这是核心能力的增量扩展，不是项目重构。需要重点控制的是研究协议：生成、筛选和最终确认必须使用彼此隔离的时间区间。

新增核心模块不得写死 `BTCUSDT`、单资产索引或时间序列专用评价方式。资产、频率、字段和评价范式通过实验上下文配置；BTC 专属逻辑只保留在数据适配器、默认配置和当前报告入口中。

## “最近实验”到底是什么

前端当前展示两类结果，含义不同：

1. **历史注册因子报告**：页面加载时读取 `reports/generated/btcusdt_1h_factor_suite_24.csv`，这是之前运行命令生成并保存的报告，不是页面刚刚自动运行的任务。
2. **页面提交实验**：点击“新建实验”后，前端调用 `POST /api/experiments`。后端创建后台任务，真实执行 `factor_lab.suite`，再由前端轮询任务状态。结果会写入 `reports/generated/api_btcusdt_*.csv/json`。

页面“最近结果”现在会分别标识历史报告和页面任务；任务行显示任务 ID、提交时间、参数和运行状态。任务元数据与结果保存到 `data/state/research_tasks.sqlite3`，服务重启后仍可查询；正在运行的任务如果在重启时被中断，会被标记为 `failed`，不会永久停留在 `running`。

自动挖掘和新建实验的关系：自动挖掘负责在训练和验证区间生成、评价和筛选表达式；用户冻结方向/风险/条件角色和信号语义后运行一次最终留出确认。方向因子只有在留出集对齐 Rank IC 超过随机 95% 阈值且成本后净收益为正时才能配置正式 ID 入库；风险与条件因子尚无专用确认协议，不能入库。顶部“新建实验”评价手工因子和已确认的正式库因子。

## 研究数据与观察数据

`data/state/datasets.json` 固定两套互不混用的数据：

- 当前研究快照：BTCUSDT 1h，2021-01 至 2026-10-11，供后续新实验和新挖掘自选研究区间；旧运行仍绑定各自原始快照和哈希；
- 当前观察快照：BTCUSDT 1h，2026-01 至 2026-10-11，用于按候选冻结边界跟踪后续收益。新研究是否使用其中日期由用户选择，不会自动改写旧候选的观察边界。

可在“数据检查”页面点击“更新数据”，也可以运行：

```bash
.venv/bin/python scripts/update_btcusdt_observation.py
```

脚本会同时更新研究快照和观察快照：研究快照默认从 2021-01 开始，观察快照默认从 2026-01 开始。对已结束月份使用月度归档，对当前月份从 1 日开始使用已发布的日度归档；遇到第一个尚未发布的日期就停止。随后同步两套资金费率、检查时间连续性、更新 `datasets.json` 并重算所有观察记录。旧研究文件和旧报告不会被覆盖，新快照只影响后续新实验/挖掘；当前不接实时 WebSocket 或自动定时任务。

使用顺序：数据检查页面点击 `更新数据` → 自动挖掘 → 验证入选候选点击 `加入观察` → 输入或用日历选择观察开始和结束日期 → 在“观察跟踪”查看状态。开始日期不能早于“验证截止 + 预测周期 purge”的边界；结束日期不能早于开始日期，未来日期也允许。表单默认填入最早合法开始和90天后的结束日期，但可自由修改。因子窗口只用于向前读取预热数据。观察区间及公式、方向、预测周期、入场分位、阈值和成本创建后不能修改。

启动自动挖掘时可以直接输入或用日历选择研究开始和结束日期，范围必须位于当前已校验研究快照内，并至少包含30天小时数据。每次运行保存自己的研究区间、数据哈希和协议版本，后续训练/验证切分、最早观察日期和最终确认都继承该运行的冻结配置。

前端左侧按实际工作流排列：`研究总览 → 数据检查 → 因子库 → 观察跟踪 → 实验记录`。因子库只负责候选生成、筛选和加入观察；观察收益及“更新观察”操作全部放在独立的“观察跟踪”页面。

## 代码结构

- `factor_lab/data.py`：单资产和多资产 OHLCV 数据契约。
- `factor_lab/sources/binance.py`：Binance K 线和资金费率数据适配器。
- `factor_lab/registry.py`：当前手工基线的因子定义和注册表；自动挖掘通过后再将候选写入目录。
- `factor_lab/factors.py`：因子计算函数。
- `factor_lab/expression.py`：安全的因子表达式树、规范化、复杂度检查和求值器。
- `factor_lab/generator.py`：按字段、操作符、窗口、二元运算和深度 3 组合均衡、确定性生成候选表达式。
- `factor_lab/mining.py`：固定训练/验证/留出边界，批量计算训练和验证指标并用验证分数排序；自动挖掘不读取留出指标。
- `factor_lab/mining.py`：还提供 `SelectionPolicy`/`screen_candidates`，按验证期指标和 FDR 状态做显式门槛筛选，并记录拒绝原因。
- `factor_lab/catalog.py`：SQLite 候选和正式因子目录，保存候选关系、淘汰原因、晋级任务、正式因子角色和信号语义。
- `factor_lab/suite.py`：统一因子评价流程。
- `factor_lab/execution.py`：执行延迟和成本模型。
- `factor_lab/benchmarks.py`：可复现的随机 Rank IC 零假设基准。
- `factor_lab/validation.py`：purged walk-forward。
- `factor_lab/service.py`：后台实验任务和 API 服务逻辑。
- `frontend/`：研究控制台。
- `tests/`：数据、因子、执行、服务和 API 相关测试。

运行测试：


当前测试状态：`78/78` 通过。`tests.test_service` 使用已下载的真实研究快照，适合作为本地集成测试；GitHub Actions 在无行情数据的环境中运行其余可移植单元测试。

表达式 DSL 示例：

```python
from factor_lab.expression import call, evaluate_expression, field

momentum_24 = call("return", field("close"), window=24)
relative_volume_24 = call(
    "div",
    field("volume"),
    call("rolling_mean", call("shift", field("volume"), window=1), window=24),
)
values = evaluate_expression(momentum_24, ohlcv_frame)
```

表达式只从传入的数据字段读取值，窗口操作只能使用当前或历史数据；结果可规范化、序列化并生成稳定 ID。面板数据可以指定资产分组层，避免时间操作跨资产串值。

候选生成器已经接入基础版，可用 `GeneratorConfig` 固定字段、操作符、窗口、最大深度、最大复杂度和最大候选数。同一配置会产生相同顺序和稳定 ID；相关性去重、SQLite 候选目录、前端挖掘任务、历史恢复和候选详情已接入。

候选筛选基础版已经接入 `mine_candidates`：默认按 60%/20%/20% 固定训练、验证和最终留出边界，并按预测周期执行 purge；候选质量、排序、稳定性、HAC/FDR 和去重只使用训练与验证区间。自动挖掘的内存结果、目录和公开报告都不包含留出指标。

`screen_candidates` 使用显式 `SelectionPolicy` 做第二阶段筛选。自动挖掘使用验证期绝对 Rank IC、方向一致性和 FDR；默认 `q=0.05` 且必须通过。持续为负的 IC 可以建议按反向语义确认，不再因符号为负直接淘汰。页面默认把验证期切成 8 个子窗口，因此一致性以 12.5% 为步长。

候选表达式同时保留英文 DSL 和中文展示公式，例如 `return(close, 24)` 显示为“24小时收益率(收盘价)”。中文仅用于阅读，计算、稳定 ID 和历史审计仍使用规范化 DSL。

最终确认会使用已冻结的信号语义和开发期固定的入场分位阈值，在留出段计算原始和方向对齐 Rank IC，并用候选 ID 派生固定随机种子执行 100 次随机秩置换。当前入库条件为：对齐 Rank IC 超过随机 95% 阈值、成本后净收益为正且相对买入持有收益为正。留出段一旦揭示便写入账本，不允许另一候选或新协议重复使用；风险和条件因子等待专用协议。

## AI + 公式混合挖掘设计（第一版已实现）

结论：该方向可行，但 AI 的职责是“受约束地提出候选”，不是判断因子是否有效。公式生成器、AI、未来的符号回归或强化学习都只是可替换的候选来源；本地确定性评价器仍是唯一裁判。因此本次不重写数据、DSL、挖掘、目录或前端主流程，而是在候选生成和统一评价之间增加一个受审计的 AI 提议适配器。

```text
确定性公式生成器 ─┐
                  ├→ AST 本地校验与规范化 → 统一预算/去重 → 训练/验证/FDR → 人工观察或最终确认
AI 结构化提议 ────┘
```

本次实现边界：

- 使用当前项目配置的 `qwen-cn / qwen3.6-plus` OpenAI 兼容工具调用输出结构化结果；模型只能返回研究假设、因子族和现有 DSL AST，不能返回或执行 Python/SQL/任意代码；
- 请求只包含字段、允许的操作符/窗口、复杂度限制和研究语境，不上传价格序列、验证结果、留出结果或观察收益；
- AI 候选必须再次通过本地 `Expression.from_dict`、字段、窗口、深度、复杂度和 canonical 去重检查；
- AI 与公式候选使用同一训练/验证、HAC/FDR、相关性去重和目录规则，来源不提供排名加分；
- AI 不读取最终留出，不触发最终确认，不自动加入观察或正式因子库；
- 密钥、模型、网络、拒绝或结构化响应异常时，整次任务回退为公式模式，并在运行审计中记录原因；API Key 不写入任务、报告或日志；
- 第一版只做一次 AI 提议，不实现“根据验证结果继续问 AI”的循环，避免反复试探验证集。

第一版验收标准：

1. `AI + 公式` 模式配置有效时，至少一次真实适配器调用可产生受限 AST，并在候选表显示 `ai` 或 `deterministic + ai` 来源及研究假设；
2. 非法字段、未知操作符、越界窗口、过深公式和重复公式全部在本地被拒绝并计入审计；
3. AI 候选与公式候选共同受 `max_candidates` 总预算约束，不因启用 AI 无限制增加多重检验数量；
4. 无配置或调用失败时公式挖掘照常完成，前端明确显示回退原因；
5. 自动化测试不访问网络，覆盖成功、非法响应、去重和回退路径；运行报告保存 provider、model、prompt version、token 数和候选审计，不保存密钥。

开源方案只借鉴结构，不直接整体引入：Qlib 的表达式引擎与数据/表达式分层适合作为长期接口参考；AlphaGen 的表达式、独立评价器和候选池设计与本项目最接近；PySR 适合作为后续可插拔符号搜索源。当前项目已有 DSL 和评价协议，直接替换为这些框架会带来数据格式、依赖和研究协议迁移成本，收益低于先完成上述最小闭环。

## 下一阶段设计：受控多轮 AI 与公式变异（仅设计，尚未实现）

目标不是让 LLM 直接筛选或批准因子，而是把当前“一次生成”升级为有预算、有父子关系、有训练反馈的候选搜索系统。AlphaGen、RD-Agent、AlphaForge、遗传编程和 GFlowNet 只作为搜索方法参考；现有 DSL、时间隔离、FDR、成本模型、候选目录和人工确认继续作为统一主干。

```text
确定性枚举 ─────────────┐
                        │
非 AI 公式变异/交叉 ────┼→ 规范化与总预算去重 → 统一验证/FDR/相关性去重
                        │                         ↓
三轮受控 AI 搜索 ───────┘                  观察或最终确认
      ↑
仅接收训练期失败摘要
```

### 1. 默认候选预算

单次运行默认总预算仍为 200，不因增加搜索器而扩大统计试验数量：

| 候选来源 | 默认预算 | 职责 |
|---|---:|---|
| 确定性公式枚举 | 100 | 保证基础搜索空间覆盖和可复现基线 |
| 非 AI 公式变异/交叉 | 60 | 围绕训练期较优表达式做窗口、操作符和子树搜索 |
| LLM 受控生成 | 40 | 提出有经济含义且与已有候选不同的因子族与表达式 |

所有来源共享同一 canonical 去重、复杂度限制和最终 200 个候选上限。某来源预算未用完时可以回填给确定性枚举，但不得在看到验证结果后追加候选。

### 2. 三轮 AI 搜索协议

最多执行三轮，三轮合计不超过 AI 预算：

1. **因子族覆盖**：按趋势、反转、波动率、成交量、价格位置、流动性和状态条件提出不同研究假设；
2. **训练期变异**：只根据训练期质量、缺失率、复杂度、方向稳定性、换手诊断和重复关系修改候选；
3. **新颖性补充**：优先补充与当前候选输出相关性较低、因子族覆盖不足的表达式。

LLM 请求不包含原始行情、逐时点收益、验证指标、留出结果或观察收益。系统只提供离散化和截断后的训练摘要，例如“方向漂移”“换手过高”“与候选 X 高度重复”，避免模型记忆或反推出具体样本。

### 3. 非 AI 公式变异器

第一版实现以下可复现操作，并由固定随机种子控制：

- 窗口替换：例如 4 小时替换为 8、12 或 24 小时；
- 操作符替换：在类型兼容的滚动或一元操作符之间替换；
- 子树替换：用合法字段或时间操作子树替换原子树；
- 公式交叉：组合两个父表达式，但不得超过深度和复杂度限制；
- 简化：删除恒等式、重复取负、同字段自减/自除等无效结构；
- 反向候选：仅改变语义或规范化取负，不复制统计等价公式。

变异器只能操作现有 AST，不能生成 Python、SQL 或字符串表达式，也不能访问未来数据。

### 4. 数据隔离

候选产生和迭代只使用训练区间；所有候选冻结后，验证区间只统一读取一次。验证结果只能用于本次筛选、FDR 和相关性去重，不能再反馈给生成器。最终留出和观察数据继续完全不可见。

```text
训练集：生成、变异、训练反馈
验证集：一次性筛选、FDR、相关性去重
最终留出：冻结后一次确认
观察数据：冻结候选的后续跟踪
```

### 5. 审计字段

候选目录计划新增：

- `source`：deterministic / mutation / ai；
- `generation_round`：生成轮次；
- `parent_expression_ids`：一个或两个父公式 ID；
- `mutation_type`：窗口替换、操作符替换、子树替换、交叉或简化；
- `hypothesis_family` 和 `ai_hypothesis`；
- `training_feedback_codes`：结构化失败或改进原因；
- `prompt_version`、provider、model 和 token 使用量；
- `random_seed`、预算使用量和提前终止原因。

不保存 API Key、原始模型思维过程或未脱敏的市场数据。

### 6. 前端设计

自动挖掘表单计划增加“高级搜索设置”，默认折叠：

- 候选总预算和三类来源预算；
- AI 轮数，允许 1–3 轮；
- 公式变异开关与固定随机种子；
- 每轮任务进度和实际 token 使用量。

候选列表和详情增加来源、轮次、父公式、变异类型、研究假设和训练反馈。验证结果仍与训练反馈分区显示，避免用户误以为 AI 看过验证或留出数据。

### 7. 验收标准

1. 相同数据版本、配置和随机种子产生相同的非 AI 候选；
2. 三类候选合计不超过总预算，AI 请求失败时剩余预算回填公式枚举；
3. 自动测试证明生成器无法读取验证、留出和观察结果；
4. 每个变异候选都能追溯到父表达式和变异操作；
5. 所有候选统一经过 AST、安全时间操作、FDR 和相关性去重；
6. 多轮搜索相对单轮基线至少提高合法候选率或独特因子族覆盖，不能只比较最高 Rank IC；
7. 旧运行和第一版 AI 报告仍可读取，协议版本升级后不与旧协议直接比较。

### 8. 明确后置内容

以下内容不纳入这次核心改造：AlphaForge 动态组合、PPO/GFlowNet 训练、多资产横截面搜索、AI 自动最终确认、AI 自动入库和实盘下单。动态组合至少等积累 10–20 个经过独立观察的候选后再评估；强化学习搜索作为独立候选后端，不替换现有评价协议。

可直接运行完整挖掘命令：

```bash
.venv/bin/python scripts/run_factor_mining.py \
  data/raw/binance_um/BTCUSDT/1h/BTCUSDT-1h-2021-01_to_2025-12.csv \
  --max-candidates 200
```

命令会生成 `reports/generated/btc_factor_mining_<run_id>.csv/json`，并将同一批候选写入 `data/state/factor_catalog.sqlite3`。候选报告不计算最终留出和未分类交易收益；冻结角色与语义并运行最终确认后，独立报告才输出留出指标。

## 长期路线

项目长期定位保持开放，当前路线按“先用 BTC 完成自动挖掘闭环，再扩展研究范式”推进：

1. 接入 2026 年新增未见数据，再校准方向一致性、FDR、入场分位和入库门槛；
2. 为风险因子实现仓位缩放协议，为条件因子实现条件分组和过滤增益协议；
3. 增加表达式类型系统和中间结果缓存，再评估 PySR/gplearn 搜索后端；
4. 完善跨运行比较、导出、候选生命周期和正式因子停用/版本管理；
5. 在协议稳定后扩展真实多资产、横截面因子和其他策略；
6. 最后接入多频率、盘口、paper trading 和实盘；LLM 保持研究辅助和候选来源，不成为有效性裁判。

## 开源项目借鉴结论

- [Qlib](https://github.com/microsoft/qlib)：借鉴表达式引擎、缓存、数据处理和完整研究流水线；不直接迁移其股票数据假设。
- [AlphaForge](https://github.com/DulyHao/AlphaForge)：借鉴“因子挖掘 → 因子组合”的分阶段流程和 train/valid/test 隔离；其实现依赖 Qlib，先参考方法，不直接作为 BTC 运行时依赖。
- [PySR](https://github.com/MilesCranmer/PySR)：作为后续符号回归搜索后端候选，借鉴复杂度与拟合效果的 Pareto 选择；需要先适配时间序列目标、purge 和成本评价。
- [Crypto AlphaForge](https://github.com/warren618/AlphaForge)：借鉴加密永续场景的滚动 IC、FDR、Newey-West/HAC、资金费率和下一根开盘执行审计；代码质量和维护状态需要单独验证，不直接复制。
- [RD-Agent](https://github.com/microsoft/RD-Agent)：后期作为研究辅助和实验编排参考，不作为当前自动生成器。它的量化场景本身采用“提出想法 → 实施 → 根据数据反馈迭代”的闭环，但当前项目先用确定性搜索建立可信基线。

更完整的研究背景和设计约束见 [时间序列动量论文中文研读.md](时间序列动量论文中文研读.md)，开发状态见 [开发进度.md](开发进度.md)。

## 安全与数据

- `.env`、原始行情、生成报告和本地状态库默认不会提交到 Git；
- API Key 只从进程环境或本地 `.env` 读取，不进入前端、日志、任务结果或研究报告；
- AI 只能提出受限 DSL AST，不能执行任意 Python、SQL 或交易指令；
- 自动挖掘不会读取最终留出指标，实盘交易不在项目范围内。
